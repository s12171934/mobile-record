# 시나리오 자동 실행과 속도

> 에이전트로 검증한 반복 케이스의 보관·재생·속도 설정 방법을 설명한다.

- 에이전트가 먼저 실행해 동작과 기대 상태를 확인한 반복 케이스에 사용한다. 새 흐름은 개별 snapshot/tap/key로 확인하고, 안정적인 반복 구간을 시나리오로 옮긴다. 녹화 관찰자는 기존 record 명령으로 별도 실행한다.

## 반복 케이스를 보관하는 방법

- 같은 확인을 다시 수행하게 되거나 회귀 확인에 계속 쓸 것이 분명하면 스크립트화한다. 한 번 쓰고 끝나는 작업이나 아직 분기가 불명확한 경로는 에이전트 방식으로 유지해도 된다.
- 통과한 경로에서 초기 상태, selector, 기대 결과, 필요한 대기 조건, 복구 동작을 추린다. 실패한 탐침·오입력까지 포함된 events.jsonl을 그대로 실행 시나리오로 변환하지 않는다.
- 소스 JSON은 프로젝트의 기존 테스트/시나리오 폴더에 목적을 알 수 있는 이름으로 저장한다. 별도 테스트 저장 위치가 없다면 해당 프로젝트의 로컬 케이스 폴더를 정해 계속 사용한다. 앱별 케이스·계정·환경 값은 공통 스킬에 섞지 않는다. 여러 케이스가 공유하는 일반 실행 기능만 스킬 scripts로 옮긴다.
- 케이스 설명이나 프로젝트의 기존 목록에 목적, 초기 상태와 복구 상태, 대상 앱/화면·언어·뷰포트 조건, 입력 인자, 검증 방식(each/batch), 최근 통과 날짜·환경과 증거 위치를 남긴다. 안정적인 케이스 ID나 파일명으로 찾을 수 있게 한다. 특정 기기 ID·터널·세션·자격증명은 실행 시 받는다.
- 초안은 실기기 재생이 통과한 뒤 재사용 가능한 케이스로 취급한다. 결과가 이미 검증된 실행이면 그 근거를 연결하고 불필요하게 반복하지 않는다. 영상·로그·결과는 실행별 run 폴더에 두며, runner는 전달받은 시나리오를 그 폴더의 scenario.json으로 복사한다.
- 다음 작업은 기존 케이스를 먼저 찾는다. 목적과 현재 전제 조건이 맞으면 최신 초기 화면을 확인한 뒤 재사용한다. 화면이나 키 배치가 바뀌거나 실행이 실패하면 중단하고 에이전트 관찰로 돌아간다. 원인을 확인한 뒤 원본을 수정하고 재생 검증을 통과해야 다시 사용한다.

- 따라서 한 작업 안에서도 에이전트가 가변 구간을 처리하고, 저장된 스크립트로 반복 확인을 수행한 뒤, 결과를 보고 다음 동작을 선택할 수 있다. 아래 SCENARIO는 보관한 소스 파일이고 RUN은 매번 새로 만드는 실행 증거 폴더다.

```bash
"$ATEST" run --label '모바일 시나리오' -- python3 "$SKILL/scripts/run_scenario.py" --run "$RUN" --scenario "$SCENARIO" --speed 2 --tap-interval 0.4 --key-interval 0.8 --key-checkpoint batch
```

- 실행 전 `--validate-only`로 구조를 확인할 수 있다. 실행 결과가 이미 있는 run 디렉터리는 덮어쓰지 않는다. 케이스가 실패하면 다음 동작으로 넘어가지 않고 종료한다. 복구 화면을 확인하고 새 run 폴더에서 재실행한다.

## 속도와 관찰

- speed는 동작 간격을 나누는 배수다. 위 설정은 탭 최소 간격 0.2초, 키 탭 최소 간격 0.4초다. 간격은 동작 시작 사이의 최소값이며 기기·RPC 처리 시간이 더 길면 그 시간이 우선한다.
- key-checkpoint each는 매 키 이후 UI와 화면을 저장한다. expectedValues가 있으면 각 조합값도 비교한다.
- key-checkpoint batch는 keys 단계에 stableLayout: true가 있을 때만 좌표를 재사용한다. 각 키는 실제 네이티브 탭이며 최종 focusedValue를 검증한다. 그 외에는 each로 실행한다.
- Shift, 숫자·언어 전환처럼 배치가 달라지는 구간은 단계로 나누거나 each로 관찰한다. batch의 중간 조합값을 확인했다고 보고하지 않는다.
- wait는 고정 sleep 대신 기대 상태가 보이면 즉시 완료한다. timeout 기본 15초, poll-interval 기본 0.25초다. 진행 중인 기기/RPC 조회 시간은 추가될 수 있다.
- 활성 display·방향·window·foreground를 확인한다. 조건이 바뀌면 좌표 재사용을 중단한다. 동일 기기의 자동 실행은 잠금으로 직렬화한다.

## JSON 형식

```json
{
  "name": "키보드 입력 예시",
  "bundleId": "example.bundle.id",
  "cases": [{
    "name": "한글 조합",
    "steps": [
      {"action": "tap", "selector": {"label": "검색", "elementType": 49}},
      {"action": "wait", "expect": {"keyboard": true, "focused": true}},
      {"action": "keys", "labels": ["ㄱ", "ㅏ", "ㄴ", "ㅏ"],
       "stableLayout": true, "expectedValues": ["ㄱ", "가", "간", "가나"], "expected": "가나"}
    ]
  }]
}
```

- 예시 bundleId와 selector는 대상 앱의 관측값으로 바꾼다. 입력 전 선택 영역·기존 값도 초기 상태 조건으로 정한다. 허용 action은 tap, wait, keys다. 문자열 주입·임의 셸 명령 실행 action은 없다.

- tap.selector는 raw AX 속성의 정확한 일치다. elementType은 Button=9, Key=20, StaticText=48, TextField=49다. 활성 화면에서 보이는 중심점이 하나여야 한다. 중복된 동일 좌표는 하나로 취급한다. 화면 가림 여부는 처음 시나리오를 만들 때 스크린샷으로 확인한다.

- tap.point: [x, y]도 지원하지만 이때 루트 viewport: {width: 951, height: 669}처럼 관측한 window 크기가 필요하다. 이 숫자는 예시이며 대상 기기와 다르면 실패한다. selector가 가능한 곳은 selector를 쓴다.

- wait.expect는 label, keyboard, focused, focusedValue를 지원하며 여러 조건은 모두 만족해야 한다. 비어 있는 focusedValue는 빈 입력을 뜻한다. 단계별 timeout을 지정할 수 있다. keys.expected는 최종 문자열이며 검색·전송 키를 자동으로 추가하지 않는다.

## 결과와 시간 비교

- scenario-results.json에는 전체·케이스·단계 시간, 실제 키 모드, 키 탭 구간 시간과 판정이 저장된다. scenario-*.png/ui.json에는 검증 지점 근거가 남는다. events.jsonl에는 모든 실제 탭과 키 label을 기록한다.

- 같은 초기 화면·시나리오·기기에서 each와 batch를 각각 한 번 실행해 비교한다. 러너 설치·기동·녹화 초기화 시간은 시나리오 실행 시간과 구분한다. 사람이나 에이전트의 판단 대기가 포함된 과거 기록은 참고값으로만 제시한다. 재생 속도를 바꿔 실행이 빨라진 것처럼 보고하지 않는다.
